# API Contract — Firefly MVP

This is an implementation contract, not an OpenAPI file. Implement request/response Pydantic schemas matching it.

## Authentication assumption

For the initial single-user hackathon demo, use a configured bearer token (`FIREFLY_API_TOKEN`) and map it to one fixed owner identifier such as `demo-owner`. The token is for development/demo, not a production identity system. All secret operations require authentication. Never expose this token to a browser bundle or log it.

## `POST /secrets`

**Purpose:** create a new secret record and distribute a share to each of the three active providers.

Request JSON:

- `secret`: non-empty string, max 4 KiB UTF-8 encoded bytes for MVP.

Optional header: `Idempotency-Key` (opaque random value generated by caller). If implemented, scope it to the authenticated owner and retain no secret in the idempotency record. If duplicate submissions are not implemented in the first milestone, explicitly document that a client retry may create a second record; do not pretend the API is idempotent.

Success `201`:

- `record_id`: random opaque ID
- `status`: `AVAILABLE`
- `share_count`: `3`
- `threshold`: `2`
- `created_at`: the persisted record creation timestamp (UTC), identical to the value later returned by the status endpoint

A secret must never be echoed in the response.

Possible errors: `400` invalid payload; `401` missing/invalid authentication; `413` payload too large; `502`/`503` external dependency failure; `500` generic unexpected error. If partial storage exists, response may include a random `operation_id` and safe status, but never ciphertext, shares, keys, credentials or raw provider exceptions.

## `POST /secrets/{record_id}/recover`

**Purpose:** recover the secret from two distinct valid shares.

Request body: empty or a minimal request ID if required for audit; secret is not sent again.

Success `200`:
- `record_id`
- `secret`: reconstructed original secret (the only endpoint that returns it)

Headers: `Cache-Control: no-store`, `Pragma: no-cache`.

The response is sensitive and must not be logged or cached. Validate owner and `AVAILABLE` status before contacting providers. The orchestrator must collect the configured number of distinct, valid shares from the correct record/version. If fewer than the threshold are obtained, return a generic recoverability error such as `503` or `409` without revealing which providers held valid shares.

## `GET /secrets/{record_id}/status`

**Purpose:** show status to an authorized owner.

Success `200` fields may include: `record_id`, `status`, `threshold`, `share_count`, `confirmed_shares` count, `created_at`, `updated_at`. The owner identifier is not returned. Do not return secret/ciphertext, key material, credentials, or internal exception strings. Require authentication and owner authorization.

## `GET /health`

The current implementation returns `{"status":"ok"}` without checking SQLCipher or provider readiness. Do not use this endpoint alone to claim operational readiness. It must not expose DB paths, provider hostnames, key references, credentials, account IDs or detailed errors. Use the separate local preflight and a synthetic end-to-end test to verify dependencies.

## Deletion

No public `DELETE /secrets/{id}` endpoint in initial MVP. `delete_share()` remains required internally for rollback after failed writes. Public permanent deletion can be added later with a documented retention/tombstone policy.

## Error handling

- Request validation failures return `422` with only the field location and error type. The submitted value is never echoed, because it may be a secret.
- A secret over the byte limit returns `413` (`HTTP_413_CONTENT_TOO_LARGE`).

- Map internal errors to stable error codes.
- Do not return provider exception text to the client.
- Avoid different public errors that reveal whether a specific share/provider is present unless needed for the UX.
- Do not log request bodies or recovery responses.
